# 실패 로그: 배포

## 1. 도구의 기본 프로젝트 폴더가 다른 프로젝트였다
- **증상**: 파이어베이스 연결 도구의 현재 폴더와 활성 프로젝트가 이 블로그가 아니라 다른 실습(`petfriends_consult_chat`)이었다.
- **원인**: 도구가 마지막으로 연 폴더를 기본값으로 쓴다. 그대로 배포하면 엉뚱한 프로젝트에 올라갈 수 있었다.
- **해결**: 이 저장소 폴더에서 `firebase deploy --only hosting --project myblog-test-54f1c`처럼 프로젝트를 직접 지정해 배포했다.
- **재발 방지**: 배포 전에 현재 폴더와 프로젝트 ID를 확인하고, 명령에 `--project`를 항상 붙인다.

## 2. 수정한 화면이 바로 보이지 않았다
- **증상**: 스타일을 고쳐 배포했는데 브라우저에는 옛날 모습이 그대로 남아 있었다.
- **원인**: 호스팅 기본 캐시가 1시간(`max-age=3600`)이라 브라우저가 옛 CSS를 계속 썼다.
- **해결**: `firebase.json`에서 `Cache-Control: no-cache`를 주었다. 처음에는 `**/*.@(html|css|js)`로만 지정했는데, 첫 화면 주소 `/`는 여기에 걸리지 않아 1시간 캐시가 남았다. 지금은 `**` 전체에 적용한다.
- **재발 방지**: 배포 뒤 확인은 일반 새로고침으로 한다. 안 바뀌면 캐시부터 의심한다.

## 3. 규칙 파일이 저장소에 올라갈 뻔했다
- **증상(예방 기록)**: `firestore.rules`에 관리자 이메일이 들어 있어 공개 저장소에 그대로 올라가면 노출된다.
- **해결**: `.gitignore`에 넣어 저장소에서 뺐다. 규칙을 바꾸면 로컬에서 직접 배포한다.
- **재발 방지**: 커밋 전에 `git status`로 새로 올라가는 파일을 확인한다.

## 4. 작업 폴더가 임시 위치였다
- **증상(예방 기록)**: 저장소 사본이 임시 폴더에 있었다. 정리되면 사라지고, 깃헙에 올리지 않은 `firestore.rules`도 함께 사라질 수 있었다.
- **해결**: 실습 폴더 안 `myblog-test`로 옮겼다(`.git`과 규칙 파일 포함).
- **재발 방지**: 작업은 이 폴더에서만 한다. 규칙 파일은 깃헙에 없으므로 이 폴더를 지우지 않는다.
